feat(P8): 自定义出站 / 路由规则 / 链式代理

数据层（迁移 v10）
- outbounds 表：tag / protocol / settings / stream / proxy_tag（链式前置）/
  send_through（绑定源地址）/ 排序
- routing_rules 表：kind（domain/ip/port/inbound/protocol/source/user）/
  values（JSON 数组）/ outbound_tag / 排序
- DeleteOutbound 会拒绝删除仍被引用的出站（被规则引用或被其它出站作为链式前置）

配置生成（internal/xrayctl）
- BuildInput 接受完整期望状态（入站 + 客户端 + 出站 + 路由规则）
- **顺序即语义**，这一点在实现里写进了注释与测试：
  * 自定义出站排在 direct/block 之前（它们会被规则或链式引用）
  * 自定义路由规则排在内置 api/block 规则之前
    —— Xray 按顺序匹配，把宽泛规则放前面会吃掉所有流量
- 渲染前做三类引用完整性校验，任一不满足直接失败：
  * 链式出站的前置必须存在且启用
  * 路由规则指向的出站必须存在（direct/block 是内置的）
  * 出站 tag 不能重复
  这些校验的价值在于：**在构建阶段就暴露问题**，而不是把一份 Xray 起不来的配置
  下发到 Agent 侧才炸 —— 那时错误出现在远端日志里，排障链路很长

接口
- GET/POST/PATCH/DELETE /api/admin/outbounds
- GET/POST/PATCH/DELETE /api/admin/routing-rules
- 创建链式出站但前置不存在时**不回滚**，只返回 warning：
  用户可能打算稍后再建前置出站；但下发配置时会明确失败

测试

  7 种规则类型映射、坏输入三种拒绝、
  配置包含顺序正确、悬空链式引用拒绝、悬空规则出站拒绝、
  重复 tag 拒绝、禁用项忽略、规则类型名稳定性
